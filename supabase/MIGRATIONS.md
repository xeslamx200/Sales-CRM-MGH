# Migrations 970-996 (applied)

These migrations were written and reviewed one by one, tested on disposable scratch databases, and then applied to **Staging**
(`oqwmgtayvsmbobwaunph`) after explicit approval of each file by its SHA-256, with a backup and a dry run before every push. They now live
in `supabase/migrations/` with the base migrations, so a new database (production) is built from that folder alone, in file-name order.

* The SQL files are byte-identical to what was applied on Staging (their header comments still say "PROPOSED": that is the review history,
  not the current state).
* Rollbacks: `supabase/rollbacks/` (each one refuses while data it would destroy exists).
* Database tests: `supabase/tests/db/20_*.sql` to `34_*.sql`.

Every file has a rollback in `rollbacks/`. The rollbacks restore the exact previous function bodies and refuse (with counts) instead of deleting data.

Scratch use only: `EXTRA_SQL="supabase/migrations/…" LOCAL_DB_NAME=<name containing scratch> bash scripts/db/test.sh` applies them on top of the committed
migrations before running the 19 SQL test files (see `scripts/db/reset-local.sh`). Concurrency tests: `scripts/db/concurrency/README.md`.

The TypeScript protocol `v2` (`KAPSO_PROTOCOL=v2`, `src/lib/kapso/v2.ts`) only works after migration 1 (and should have 2, 3 and 5) plus 6 (`978`: protocol v2 calls its functions). A real Coexistence number needs 7 (`979`) first. The default protocol `v1`
and the admin edit (which falls back to the plain table update when file 4 is absent) keep working without any of them.
